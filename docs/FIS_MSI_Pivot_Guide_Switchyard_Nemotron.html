MSI Experimentation Pivot Guide

FIS → System-of-Models Routing

How to pivot the existing Fintech Integration Sandbox toward NeMo Switchyard, Nemotron 3.5 Lightning, and measurable strong/weak routing—without throwing away the work already completed.

Status reference: 2026-08-15 · repo ~/projects/fintech-integration-sandbox · baseline commit da35ab3 · eval suite v2

Starting point

This guide assumes the FIS repository is at commit da35ab3, the event-driven migration is complete, eval suite version 2 is the active comparable suite, E6 is confirmed on test, and E6b is the only experiment currently in flight. The one unconfirmed status figure is the post-E6b full-suite test count; rerun make test before recording the next baseline.

Executive Summary

FIS should pivot toward a system-of-models and routing experiment without restarting the project. The current implementation is already more valuable than a fresh Switchyard/Nemotron demo because it has deterministic world generation, objective ground truth, model-independent evidence reachability checks, a strict dev/test protocol, per-dimension scoring, and enough arm disagreement to expose harness bugs.

The immediate change is not “replace the local model with Nemotron” and not “move the platform into NeMo.” The immediate change is to introduce a thin model-routing boundary, use NeMo Switchyard as the leading implementation candidate behind that boundary, add Nemotron 3.5 Lightning as a candidate weak/specialist execution model, and evaluate hybrid routing with the same causal discipline already used for E6/E6b.

Why this is a routing testbed now

The local and frontier arms have a very large quality gap, but the local arm is no longer uniformly weak: prompt structure moved diagnosis from 16.7% to 65.6% and made action selection perfect conditional on correct diagnosis. That means some cases are already cheap-model-solvable while others still require stronger reasoning. Routing is now a measurable optimization problem rather than an architectural slogan.

What the Current Results Say

The most important result is not simply that E6 improved strict all-pass from 3.1% to 29.2%. It is that the experiment separated three different failure mechanisms:

  • Hypothesis consideration: enumerating the 12 cause labels recovered most of the diagnosis gain.
  • Policy lookup: the cause→action map drove act | rc to 100%.
  • Evidence discipline: once diagnosis and action improved, required-evidence recall became the dominant loss.

This is exactly the behavior expected from a mature learning harness: improvement in one dimension exposes a new bottleneck instead of being flattened into a single aggregate score.

Cutover Sequence from da35ab3

  1. Do not interrupt E6b. Finish the 2×2 dev sweep exactly as designed.
  2. Select the E6b winner on dev and run the single test confirmation once.
  3. Rerun make test and record the actual full-suite count; this closes the only unconfirmed figure in the status report.
  4. Run make reachability; require 96/96 and zero capped classes.
  5. Freeze the prompt/evidence/model configuration as the local routing baseline. Do not modify it during the first Switchyard equivalence test.
  6. Create a new routing experiment namespace (R0…R5) rather than consuming or renumbering the existing E-series.
Do not mix the pivots

Do not simultaneously change prompt wording, evidence rules, local model, gateway, and router. Your current project has succeeded because it tests factors. Keep that discipline. The first Switchyard experiment must be a zero-semantic-change transport experiment.

That boundary keeps Switchyard replaceable. If it proves excellent, it remains. If a future router is better, FIS can swap the routing implementation without rewriting the eval harness or the business system.

New Routing Experiment Track

Create a separate R-series so routing experiments cannot be confused with prompt/context experiments.

R0 — Freeze the E6b Local Baseline

Question: What is the best causally selected local configuration before routing is introduced?

  • Finish E6b on dev.
  • Confirm the winner on test once.
  • Record exact prompt version, model build, quantization/runtime, suite v2, corpus seed/version, evidence mode, and scorer version.
  • Freeze this configuration as weak-baseline-v1.

Exit criterion: a reproducible baseline run plus a clean make test and make reachability.

R1 — Switchyard Passthrough Equivalence

Question: Can Switchyard sit in the model path without changing semantic outcomes?

R1
orchestrator → Switchyard :4000 → same local model :8082
  • Use a single-model passthrough profile.
  • Keep prompt, evidence, model, decoding parameters, grammar/schema, and scorer unchanged.
  • Compare scenario-by-scenario outputs, parsing, scores, latency, and token usage.
  • Any quality delta is a transport/configuration bug until proven otherwise.

Exit criterion: semantic equivalence within expected nondeterminism, with route/backend metadata captured for every request.

R2 — Paired Strong/Weak Opportunity Map

Question: Before inventing a router, how much routing opportunity actually exists?

Join weak and strong results by scenario ID on dev and calculate the counterfactual outcome matrix:

WeakStrongMeaningRouting implication
passpassWeak is sufficient.Ideal cheap-model coverage.
failpassStrong can rescue.Router must escalate these cases.
passfailModel diversity / strong regression.Do not assume “strong” dominates every class.
failfailNeither model solves it.Likely system/context/harness or new capability work.

Add a script such as scripts/routing_oracle.py that reports the oracle strong-call minimum: the best possible strong-model utilization if a perfect router knew which cases the weak model would pass. This sets a ceiling for router research and tells you whether the optimization is economically meaningful.

Do this on dev, not test

The oracle analysis is a selection tool. Use dev to design the routing policy. The final chosen policy gets one test confirmation, preserving the existing methodology.

R3 — Nemotron 3.5 Lightning Candidate Arm

Question: Does Nemotron 3.5 Lightning improve the weak/specialist frontier before any specialization?

  1. Compatibility spike first. Verify the current model card/checkpoint, quantization, license, supported runtime, and healthy VRAM margin for the MSI's 16 GB GPU. Do not infer memory fit from “active parameters” alone.
  2. If local packaging is not yet mature, run the model through an NVIDIA/hosted endpoint first. This separates model capability from local serving compatibility.
  3. Run the identical prompt, evidence set, grammar, and scorer used for the frozen weak baseline. Do not tune the prompt for Lightning in this first comparison.
  4. Compare strict all-pass, root cause, act | rc, evidence recall, verifier, parse rate, unsupported/forbidden claims, latency, tokens, and cost.
  5. Only after the model-only arm is measured may a separate dev-only Lightning prompt adaptation be tested.
Lightning is a candidate, not a dependency

It was announced only days before this pivot. Switchyard has a documented public implementation surface today; Lightning's exact packaging and local-runtime details are moving quickly. Treat the first integration as a compatibility/evaluation spike, not as a rewrite of FIS around one model.

R4 — Deterministic Cascade Routing

Question: How far can you get without a learned router?

request
  ↓
weak model
  ↓
production-available checks
  ├── parse/schema failure ─────────────→ strong
  ├── deterministic verifier failure ──→ strong
  ├── tool/backend failure ─────────────→ strong or retry
  ├── unsupported-claim detector ──────→ strong
  └── checks pass ─────────────────────→ accept weak

Use only signals that would exist in a real deployment. Do not route using gold root cause, scenario ID, or required-evidence recall; those are eval labels, not production signals. Eval-only evidence recall can measure router regret after the fact, but it cannot be an online routing feature.

R4 is important because deterministic gates are interpretable and often capture the easiest escalation wins. It also tells you what residual error remains for a learned Switchyard classifier/stage router.

R5 — Predictive / Stage Routing

Question: Can a router predict weak-model insufficiency before or during execution while preserving a pre-registered quality floor?

Candidate feature families:

  • Pre-inference: evidence volume, services implicated, temporal span, presence of reconciliation mismatch, number/type of provider events, tool availability/failures, task complexity metadata.
  • Post-weak: parse success, deterministic verifier result, unsupported-claim checks, contradiction signals, tool failure state, structured confidence if empirically calibrated.
  • Session/history: only later, if the sandbox evolves into multi-turn investigations; Switchyard's stage-router ecosystem supports signal/history-based routing patterns.

Compare at least three policies on dev: deterministic cascade, Switchyard LLM-classifier routing, and a simple transparent baseline (for example a logistic model or decision tree over production-available features). Complexity must earn its place.

Pre-register the quality floor on dev in case counts as well as percentages. With 96 test scenarios, one case is roughly one percentage point, so “no more than one additional strict failure versus strong-only” is more interpretable than a vague percentage target. Choose the actual tolerance before the final test confirmation.

Methodological Rules to Preserve

  • Selection happens on dev. This now applies to prompt, model candidate, routing threshold, classifier choice, and quality/cost tradeoff.
  • Test factors, not bundles. Gateway-only, model-only, routing-only, prompt-only changes should have separate arms.
  • Do not route using eval-only truth. Gold labels and required-evidence sets may score a route; they may not choose it.
  • Never widen the rubric to accommodate model output.
  • Run reachability after every corpus regeneration.
  • Preserve prompt-rule wording constraints during the E6/E6b family so placement/content conclusions remain valid.
  • Use arm disagreement as a harness alarm. A weaker model unexpectedly beating a much stronger model on one class remains a reason to inspect the scenario/tool/scorer ceiling first.
  • Version scorer changes. If the residual forbidden-claim false positive is fixed, do not silently mutate suite-v2 comparisons. Either retain an annotated corrected metric or create a new scorer/suite version and rerun comparable arms.

Promote Harness Integrity to a Product Feature

The bugs found in this session are not incidental cleanup; they demonstrate a reusable evaluation discipline that should become part of the project itself.

BEFORE BELIEVING A MODEL FAILURE

1. Does the scenario actually contain the intended signal?
2. Can the model reach that signal through allowed tools/evidence?
3. Does the tool expose the distinguishing field?
4. Is the scorer polarity/logic correct?
5. Does the stronger arm behave as expected?
6. Only then classify the residual as model weakness.

Add a preflight report that combines scenario invariants, projection/live parity, reachability ceilings, scorer smoke tests, and model-arm sanity checks. In a future client implementation, this becomes a major differentiator: it prevents teams from fine-tuning models to compensate for broken data paths.

Before configuring the current local model as a backend, verify that the service on port 8082 exposes a supported OpenAI-compatible chat endpoint. If it does not, add the thinnest possible protocol adapter; do not change the model implementation merely to satisfy the router.

The MSI remains the right experimentation node because FIS services can occupy system RAM while the RTX 5080's dedicated VRAM is reserved for local inference. For the routing phase, prioritize reproducibility and headroom over maximum model size.

Nemotron 3.5 Lightning Integration Strategy

Do not make the MSI project dependent on a local Lightning deployment until the exact released checkpoint and serving stack are verified. The model is new enough that the integration plan should deliberately separate three questions:

  1. Capability: Does Lightning perform well on FIS with the same evidence and prompt?
  2. Economics: Is its latency/token/cost profile attractive relative to the current local model and frontier?
  3. Placement: Can the preferred checkpoint run on the 16 GB RTX 5080 with enough free VRAM for KV cache and stable service operation?

If capability is strong but local placement is poor, that is still a useful result: Switchyard lets the same model remain a cloud-hosted specialist while smaller models run locally. Model identity and model placement are separate decisions.

What the Demonstration Should Eventually Show

The strongest demo is not “FIS can call three models.” It is a controlled economic/quality story:

STRONG-ONLY BASELINE
quality: very high
cost: high
local ownership: low

WEAK-ONLY BASELINE
quality: lower
cost: low
local ownership: high

HYBRID ROUTE
quality: close to strong-only
cost: materially lower
strong-call rate: reduced

SPECIALIZED HYBRID (later)
weak model improved from FIS trajectories/corrections
quality: preserved
strong-call rate: reduced again
cost per strict pass: reduced again

The report should show per-scenario outcomes and at minimum:

  • strict all-pass and each conjunctive component,
  • weak coverage and strong-call rate,
  • route regret and unnecessary escalation,
  • cost per strict pass,
  • latency per strict pass,
  • router overhead,
  • failure taxonomy after routing,
  • which improvements came from prompt/context, routing, model swap, or training.

That gives you a tangible claim you can later translate to real work: the platform learned to reserve expensive intelligence for the fraction of tasks that actually needed it, and the eval harness proves the tradeoff.

North Star

FIS should become a laboratory for proving that a heterogeneous company-AI system can preserve near-frontier task success while shifting as much work as safely possible to smaller, cheaper, locally controlled models—and can explain, with scenario-level evidence, why each model or route succeeded or failed.

The current implementation is not being discarded. The event migration, reachability work, scorer fixes, E6 factorization, and E6b experiment are precisely what make the routing pivot scientifically useful. The next stage is to place multiple models behind a replaceable routing layer and let the existing harness determine whether the system-of-models thesis is actually true for this workload.
