MSI AI Workstation Experimentation Guide

Clean-room Fintech Integration Sandbox reference project

Target workstation
AMD Ryzen 9 9955HX • 64 GB system RAM • NVIDIA GeForce RTX 5080 Laptop GPU • 16 GB GDDR7
Preferred development topology: Windows 11 + WSL 2 + Docker + CUDA, or native Linux if the machine is dedicated.

Purpose

Use this guide together with the Canonical Architecture document to learn the platform end-to-end on a machine where experimentation is inexpensive and unconstrained by company code. The reference project is intentionally realistic enough to teach integration, observability, evaluation, routing, and continual-learning mechanics that can later transfer to real fintech work.

Clean-room rule

Do not copy Spidr source code, internal API schemas, prompts, architecture documents, credentials, customer data, runbooks, or proprietary implementation details into this sandbox. Design all services, fields, workflows, test data, and vendor simulators independently.

Executive Summary

The recommended first experiment is a synthetic but operationally realistic fintech integration platform named the Fintech Integration Sandbox (FIS). It simulates the kinds of boundaries common in neobank infrastructure—processor events, identity verification, transaction monitoring, ledger postings, webhooks, reconciliation, and operations cases—without reproducing any employer implementation.

The learning objective

Build one complete AI loop: request → authorization → router → tool calls across microservices → evidence-backed answer → deterministic verification → trajectory capture → eval → correction → candidate improvement. The project succeeds when you can measure this loop, not merely when a chat interface works.

The MSI is ideal for this because system RAM and GPU VRAM are separate. Your microservices and databases can occupy a substantial portion of the 64 GB system memory while the RTX 5080 retains a dedicated 16 GB GPU memory pool for inference or adapter training. NVIDIA specifies the RTX 5080 Laptop GPU with 7,680 CUDA cores, 16 GB GDDR7, and 896 GB/s memory bandwidth.

What you should have at the end

  • A 7–9 service fintech sandbox with synthetic customers, accounts, cards, transactions, KYC/AML events, webhooks, and operations cases.
  • A model gateway capable of selecting local NVIDIA inference or an optional cloud/frontier fallback.
  • A read-only AI investigation workflow that gathers evidence from multiple services and produces a structured case assessment.
  • A deterministic scenario generator with known ground truth, allowing objective evals.
  • A canonical trajectory store containing model versions, prompts, context, tool calls, outputs, corrections, latency, and cost.
  • A small evaluation dashboard showing task success, evidence correctness, escalation, latency, and cost per successful investigation.
  • At least one QLoRA/SFT candidate experiment so you understand the entire improvement pipeline even if the trained adapter does not beat the baseline.

Project philosophy

START WITH:             build a deterministic sandbox

2. Recommended OS and Runtime Topology

If the MSI is currently a Windows laptop, use Windows 11 + WSL 2 rather than immediately dual-booting. This gives you the NVIDIA Linux/CUDA ecosystem while preserving the convenience of a normal Windows workstation. If the machine later becomes a dedicated AI node, native Ubuntu/Linux is the cleaner long-term server configuration.

Preferred first path

Windows host → current NVIDIA Windows driver → WSL 2 Ubuntu → Docker Desktop WSL backend → Linux project files inside WSL → CUDA-visible containers and Python environments.

  • Install/update the NVIDIA Windows driver. Under WSL, do not install a separate Linux display driver; NVIDIA exposes the Windows driver into WSL.
  • Install WSL 2 and keep the WSL kernel current.
  • Enable Docker Desktop WSL integration. Docker documents GPU support on Windows through the WSL 2 backend.
  • Keep repositories inside the WSL Linux filesystem rather than under /mnt/c for better Linux tooling and file performance.
  • Use VS Code/JetBrains remote-to-WSL workflows so the editor can remain on Windows while execution occurs in Linux.

For WSL, a reasonable starting cap on a 64 GB system is 40–48 GB, leaving Windows enough headroom. Microsoft allows the WSL 2 VM memory limit to be configured in %UserProfile%\.wslconfig. Start conservatively; increase only after observing real usage.

6. Model Serving Strategy on 16 GB VRAM

The first goal is not maximum model size. It is a stable API endpoint with enough headroom to run repeatable evals while the sandbox services remain available.

TierSuggested size classRolePlacement
Router / classifier~1B–4BTask type, risk class, escalation decisionLocal; can remain resident if inexpensive.
Primary investigator~4B–8BTool use, evidence synthesis, structured case assessmentLocal default.
Higher local capability~12B–14B quantizedHarder investigations and comparison experimentsLocal when GPU headroom is sufficient.
Large open / frontier30B+ or proprietaryComplex planning, judge, hard escalation, teacher tracesCloud / hosted API.
Starter recommendation

Begin with one instruction-tuned 4B–8B model that supports tool/function calling in your chosen runtime. Do not start with multiple local specialists. First prove the workflow, trajectory schema, and eval harness. Add a second model only when you have a measured reason.

Current open model families include Qwen3 dense models in 4B/8B/14B sizes and Gemma 4 variants intended for laptop/desktop deployment. Treat family selection as an experiment: benchmark tool-call correctness and structured-output reliability on your own FIS evals rather than choosing by generic leaderboard score.

7. When the MSI Should Still Use Cloud

  • A model does not fit comfortably in 16 GB VRAM with the required context and concurrency.
  • You need a strong teacher/planner to establish an upper-bound baseline.
  • A training run requires substantially more VRAM or would occupy the workstation for too long.
  • You need high-throughput batch generation or large-scale eval runs.
  • You want to test whether a local model failure is capability-limited: replay the same evidence to a stronger cloud model and compare.

Part II — Reference Project: Fintech Integration Sandbox (FIS)

8. Project Scope and Clean-Room Boundary

FIS is a fictional fintech platform for a fictional neobank named Northstar Bank. It exposes independently designed APIs and synthetic events representing common categories of fintech infrastructure. The purpose is to recreate the engineering shape of integration work—not any specific vendor or employer implementation.

No real financial activity

FIS uses only synthetic people, accounts, money movements, identifiers, policies, alerts, and decisions. It must never connect to production financial accounts, real customer PII, vendor credentials, or employer systems.

What it should teach

  • Microservice boundaries and cross-service data gathering.
  • Vendor-normalization patterns and webhook idempotency.
  • Event-driven workflows and eventual consistency.
  • Operational cases that require combining processor, identity, risk, and ledger evidence.
  • Tool-based AI rather than “stuff the database into the prompt.”
  • Production-style observability, trajectory capture, evals, and controlled improvement.
  • How to compare local small models against stronger cloud models using business-level metrics.

9. Product Story

Northstar Bank wants a single operations console that hides the complexity of several simulated providers. A customer applies for an account, undergoes identity verification, receives a virtual card, authorizes transactions through a processor, and has ledger postings and risk events generated asynchronously. Operations staff investigate exceptions through cases.

Customer / operator
      │
      ▼
Northstar API / Ops UI
      │
      ├── identity + onboarding
      ├── accounts + ledger
      ├── cards + processor simulation
      ├── risk / AML simulation
      ├── webhooks + normalized events
      └── operations cases

AI Investigator reads through controlled tools only.
It does not write money movement or approve/reject customers.

Primary AI use case

Operations Investigation Copilot

Given a synthetic case or incident ID, gather evidence across the platform, identify the most likely root cause, cite the relevant facts, distinguish facts from hypotheses, recommend the next operational step, and assign a confidence score. The output must conform to a schema and pass deterministic checks.

This is a strong test case because success can be objectively scored: the scenario generator knows the injected root cause and the authoritative records the model should discover.

Use normalized IDs everywhere

The simulator should deliberately create provider-specific IDs and normalized internal IDs. The AI tools should expose both where useful. Cross-system ID mapping is a realistic source of operational mistakes and makes for good evaluation scenarios.

14. Deterministic Scenario Generator

Build a scenario generator that produces complete synthetic timelines from a random seed. Each scenario writes authoritative records across services and stores a hidden ground-truth manifest. The model can query the services but never sees the manifest.

S01 Duplicate webhookProvider event delivered twice; dedupe handled correctlySame provider_event_id; duplicate attempt; one normalized event; one ledger effect.
S02 Missing idempotencyDuplicate event creates two downstream actionsTwo effects tied to same provider event; idempotency key absent/misused.
S03 KYC holdOnboarding blocked by incomplete verificationVerification pending/failed; account/card activation waiting on it.
S04 Provider outageIdentity vendor timeout delays onboardingWebhook/API failures clustered in window; no customer-specific failure reason.
S05 Processor declineAuthorization rejected for processor reasonDecline code, card/account states otherwise healthy.
S06 Ledger mismatchProcessor settlement differs from ledger postingProcessor amount/reference differs from ledger authoritative record.
S07 Reversal raceAuthorization reversed before delayed posting arrivesOut-of-order timestamps; reversal and late event visible.
S08 Risk holdTransaction alert causes account/card restrictionRisk alert precedes restriction; processor symptom is secondary.
S09 Stale integration mappingProvider field change maps status incorrectlyRaw provider event differs from normalized domain state.
S10 Reconciliation gapSettlement received but corresponding posting missingProcessor settlement exists; ledger reference absent.

S12 Compound failureWebhook retry plus KYC hold produces misleading surface symptomTwo issues exist; only one explains the customer-facing state.
Why this matters

You can generate hundreds of variations while preserving objective labels. That lets you test whether improvements generalize across amounts, timestamps, customers, providers, event orderings, and irrelevant distractor events.

17. Evaluation Suite

The benchmark should have frozen train/dev/test seeds. Do not tune against the test set. Each scenario should score several dimensions so you can see whether a change helps one capability while hurting another.

Unsupported-claim rateClaims without authoritative supportHallucination/overreach measure.
Next-action accuracyAllowed action-code matchOperational usefulness.

Escalation qualityEscalates hard cases without escalating easy onesRouter calibration.
LatencyP50/P95 investigation timeDeveloper/operator usability.

All-pass definition

CASE_SUCCESS =
    root_cause_correct
    AND required_evidence_recall >= threshold
    AND unsupported_claims == 0
    AND next_action_acceptable
    AND verifier_passed

Track component scores as well as the strict all-pass rate. A strict metric is useful because real operational tasks often fail if any one critical dimension is wrong.

For the first adapter experiment, curate only cases where the evidence was sufficient and the target correction is unambiguous. Do not train the model to compensate for broken tools, missing records, or bad scenario data.

21. First QLoRA Experiment

  1. Generate a few hundred to a few thousand diverse training scenarios, but hold out entire seeds/scenario variations for evaluation.
  2. Select only verified traces with correct tool evidence and a canonical structured answer.
  3. Convert trajectories into the chat/tool format expected by the base model. Preserve tool-call sequences if your chosen training stack supports them.
  4. Train a small LoRA/QLoRA adapter on the MSI using Unsloth/PEFT. Start with a 4B–8B model rather than maximizing model size.
  5. Evaluate the adapter against exactly the same frozen test cases as the prompt-only champion.
  6. Promote only if the improvement is meaningful and regressions on other scenario classes are acceptable.
A failed fine-tune is still a successful experiment

If the adapter does not beat the prompt/tool baseline, you have learned something important: the bottleneck may be context engineering, tool use, routing, or base-model capability. Record the result rather than forcing the fine-tune into the architecture.

If you want a slower pace

Treat each week as a milestone rather than a calendar commitment. The important sequencing rule is: do not train before the scenario/eval system is trustworthy, and do not add multiple models before one model + tools works end-to-end.

26. Your First Three Working Sessions

Session 1 — Prove the machine

  • Update/install NVIDIA driver, WSL 2, Docker Desktop WSL integration.
  • Run nvidia-smi inside WSL and the Docker GPU sample.
  • Create the repository and Python environments.
  • Serve a small local model and call it through HTTP.
  • Record GPU VRAM, tokens/sec, and idle system RAM.

Session 2 — Prove the platform shape

  • Start PostgreSQL and NATS.
  • Create customer-service and processor-sim.
  • Generate one synthetic customer and one authorization event.
  • Create an ai-orchestrator with two read-only tools.
  • Capture a trajectory containing the model call and tool calls.

Session 3 — Prove measurement

  • Create three injected failure scenarios with hidden ground truth.
  • Write an eval runner that calls /investigate/{case_id}.
  • Score root cause, evidence IDs, action code, latency, and verifier pass.
  • Run the same scenarios with a local model and a strong cloud model.
  • Save the first comparison report.
At that point you have the essence of the entire system

Everything after Session 3 is scaling, specializing, adding better diagnosis, and improving reliability. You will already understand the core architecture through a real working loop.

27. Demonstration Script

1. Open the operator UI and select a seeded incident whose root cause is hidden from the viewer.

2. Run the investigation locally. Show the live tool sequence: case → processor → ledger → webhook/risk as needed.

3. Display the structured answer with evidence references and verifier result.

4. Reveal the hidden scenario manifest and automatic score.

5. Show the trajectory record: model, prompt version, tool calls, latency, token counts, score.

6. Switch to hybrid routing and replay a difficult case that escalates to the cloud model.

7. Show the eval dashboard comparing local-only, cloud-only, and hybrid runs.

8. Optionally load the QLoRA adapter and show the regression report rather than cherry-picking one demo case.

29. Security and Safety Boundaries for the Sandbox

  • Synthetic identities only; generate obviously fictional names and identifiers.
  • No real payment credentials, PANs, SSNs, account numbers, or vendor secrets.
  • AI tools are read-only in the first project. Any “action” is an action code or simulated case update.
  • Separate hidden ground-truth manifests from model-visible service APIs.
  • Log hashed/redacted arguments where full values are unnecessary.
  • If using a cloud model, route only synthetic sandbox data. This keeps provider/privacy experimentation simple.
  • Do not claim the sandbox constitutes compliance advice or a production AML/KYC decision system.

30. Decision Gates Before Adding Complexity

Before adding…Require evidence that…
Multiple specialist modelsDifferent task families benefit from materially different models/adapters or tool sets.
Dedicated vector databasePostgreSQL/pgvector is measurably the bottleneck.
Complex agent frameworkExplicit state-machine orchestration has become unmanageably repetitive.
RL / SDPOYou have substantial high-quality trajectories, stable evals, and SFT/QLoRA is insufficient.
KubernetesOne-machine/Compose operation is genuinely blocking multi-node production needs.
Large local modelA smaller model fails despite correct evidence and a larger model passes enough cases to justify cost.
Automated self-trainingCandidate evaluation, rollback, lineage, and human release gates are already reliable.

A miniature company-intelligence factory: a realistic operational system that emits observable trajectories, an AI runtime that must use controlled tools to solve tasks, an objective benchmark that tells you whether it worked, and a learning pipeline that can improve the model or the surrounding system based on evidence.
