Fintech Integration Sandbox · Milestone R5

Learned Silent-Failure Routing

Predict when a completed local investigation is unsafe to return using only production-observable signals, then compare learned routing with R4 and the oracle.

1. Executive summary

Suite v3 moved the dominant bottleneck from benchmark realism to silent local failure: schema-valid, verifier-clean answers that are still wrong on root cause or required evidence.

R5 objective: learn a post-local-execution risk score from the answer and trajectory snapshot that production actually has before escalation.

R5 changes only the routing decision. Suite v3, models, prompts, tools, evidence, scorer, verifier and frontier configuration remain frozen.

3. Scientific question

Can production-observable trajectory and answer features identify verifier-clean local failures that deterministic R4 misses?

The target is not generic classifier accuracy. The target is fewer unsafe local returns without degenerating into “send everything to frontier.”

Null result

If the available observable features do not generalize on DEV, R5 should say so. That would point toward richer verification, better signals, or model specialization rather than an overfit classifier.

6. Dataset protocol

TRAIN
  fit preprocessing/classifier
  TRAIN-only grouped CV

DEV
  compare candidates and thresholds
  select/freeze exactly one policy per local model

TEST
  exactly-once replay after freeze
  no iteration afterward

First determine whether Suite v3 has a suitable TRAIN split and whether Qwen/Nemotron TRAIN trajectories already exist. Reuse them if present. If the TRAIN corpus exists but trajectories do not, generate only the missing frozen TRAIN arms. Do not regenerate DEV/TEST model outputs unnecessarily.

No suitable TRAIN split? Preserve TEST as holdout. Pre-register a deterministic grouped development protocol rather than casually training on TEST.

Related scenario seeds/templates must be grouped during CV so the classifier cannot memorize template structure through nearly duplicated examples.

Rule: gold may supervise the label; gold may never enter the feature vector.

Leakage guards

  • Explicit feature allowlist, not “drop known bad columns.”
  • Gold-removal invariance: deleting/perturbing gold fields leaves feature vectors identical.
  • Scenario IDs/classes/seeds cannot appear directly or indirectly.
  • Feature serialization is deterministic and versioned.
  • A production-shaped trajectory with no gold fields can still produce the snapshot.

8. Labels

Primary offline label:

safe_local = strict_all_pass

Keep diagnostic failure dimensions for analysis only: wrong root cause, required evidence miss, action failure, verifier failure, parse/no-output, unsupported/forbidden claim.

The key analysis is the verifier-clean subset: did the learned router catch failures R4 could not?

9. Router candidates

Start with low-capacity, interpretable models because the dataset is small.

  1. Existing R4 deterministic gate — incumbent baseline.
  2. Logistic regression.
  3. One shallow tree model if supported cleanly by the current dependency stack.

Train separate Qwen and Nemotron routers first. A unified model may be exploratory only. Do not use neural networks, LLM judges, frontier embeddings, or hidden reasoning content unavailable at runtime.

10. Oracle ceilings

Post-answer oracle

For Qwen and Nemotron separately, compute the ideal gate that returns a safe local answer and escalates only a local failure that the frontier can rescue. Report local-safe, rescueable, unresolved, oracle quality and minimum useful frontier utilization.

Three-tier cheapest-sufficient oracle

if Qwen passes:       Qwen sufficient
elif Nemotron passes: Nemotron sufficient
elif frontier passes: frontier required
else:                 unresolved

This is descriptive groundwork for R6, not a learned policy in R5.

11. Evaluation

Classifier metrics

Unsafe-case recall/precision, false negatives, false positives, PR-AUC, ROC-AUC where meaningful, and calibration/Brier score where useful.

Primary system metrics

  • final strict all-pass
  • routing false negatives
  • frontier utilization
  • unnecessary escalations
  • frontier rescue rate
  • cost per attempt / successful investigation
  • estimated p50/p95 latency
  • gap to oracle

Report the full DEV Pareto frontier: final quality / false negatives versus frontier utilization. A learned router that simply approaches strong-only usage is not a meaningful success.

12. Selection protocol

Before scoring candidate routers on DEV, commit an R5 experiment contract using TRAIN evidence only. It must freeze:

  • feature families and exact allowlist
  • grouped CV protocol
  • candidate classifier families
  • hyperparameter bounds
  • threshold grid/procedure
  • numeric DEV selection criteria
  • maximum acceptable escalation increase
  • TEST unlock condition

Recommended lexicographic shape:

  1. materially reduce R4 silent false negatives;
  2. do not achieve this by collapsing toward strong-only routing;
  3. among qualifying policies, prefer fewer unnecessary escalations/frontier calls;
  4. use cost/latency as secondary tie-breakers.

The exact numeric thresholds must be chosen from TRAIN and committed before DEV candidate scoring.

Expected operational improvement: R5 should be substantially faster than Suite v3 unless missing TRAIN trajectories must be acquired.

14. TEST policy

  1. Train on TRAIN.
  2. Select on DEV.
  3. Freeze artifact, preprocessing, feature schema and threshold.
  4. Then open TEST exactly once.
  5. No feature/threshold/model changes afterward.

Use the existing frozen Suite v3 TEST trajectories for replay. New TEST model calls should not be necessary.

R5.9 Stop
Recommend exactly one next milestone.

17. Acceptance criteria

  • Suite v3 unchanged.
  • R5 contract committed before DEV candidate scoring.
  • Production decision snapshot versioned and allowlisted.
  • Gold-leak tests pass.
  • Grouped memorization guard exists.
  • Qwen and Nemotron post-answer oracles computed.
  • Three-tier oracle computed descriptively.
  • R4 reproduced from frozen trajectories.
  • Interpretable learned router trained for each local model.
  • Candidate development uses TRAIN only.
  • DEV Pareto frontier and silent-FN recovery reported.
  • At most one policy per local model frozen.
  • TEST opened only for qualified frozen policies and only once.
  • No prompt/model/verifier/evidence/suite changes.
  • No R6/QLoRA/dynamic-harness work started.
  • Timing and number of new model calls reported.
  • Docs updated; working tree clean.
