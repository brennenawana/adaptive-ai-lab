Company Intelligence Platform — Canonical Architecture v1

Finalized Reference Architecture and Phased Implementation Specification

This document defines Canonical Architecture v1. Future papers, models, or tools should be evaluated against this architecture rather than continuously redesigning the system.

The system is not primarily a chatbot, an agent framework, a collection of LoRAs, or a RAG application.

It is:

A company intelligence platform that learns which combination of model, adapter, context, knowledge, tool, workflow, and verifier solves each company task most reliably—and turns every production attempt into evidence for improving the next version.

The self-improvement loop is therefore:

USE
 ↓
OBSERVE
 ↓
DIAGNOSE
 ↓
DECIDE WHAT NEEDS IMPROVEMENT
 ↓
ACQUIRE THE MISSING EVIDENCE
 ↓
FIX SYSTEM or TRAIN MODEL
 ↓
EVALUATE
 ↓
SHADOW
 ↓
CANARY
 ↓
PROMOTE / ROLLBACK
 ↓
USE AGAIN

Crucially: self-improvement ≠ autonomous self-modification.

Production generates evidence. A separate system manufactures candidate successors. Candidates have to earn their way into production.

2. A specialist is more than a model

This is an important architectural decision.

Don’t define:

sales specialist = fine-tuned Qwen model

Define:

SPECIALIST
 =
 base model
 + adapter, if necessary
 + system contract
 + permitted tools
 + retrieval policy
 + context-building rules
 + structured output schema
 + verifier
 + task rubric
 + evaluation suite

For example:

id: contract-renewal-specialist
version: 3.2.0

base_model: qwen-company-base
adapter: contract-analysis-v7

tools:
  - contracts.search
  - contracts.get_document
  - crm.get_customer

permissions:
  read_only: true

context_policy:
  max_documents: 12
  prefer_authoritative_sources: true

output_schema:
  customer:
  contracts:
  renewal_dates:
  confidence:
  citations:

verifiers:
  - date_validation
  - contract_id_exists
  - citation_required

eval_suite:
  contract-renewal-eval-v14

This gives us modularity without requiring dozens of independent models.

3. The memory architecture

Do not call everything “memory.”

There should be five distinct types.

Authoritative memory

Actual systems of record:

CRM
ERP
contract database
ticketing system
finance system
HR systems
company databases

The AI doesn’t “remember” these. It queries them.

Knowledge memory

Documents and relatively static company knowledge:

policies
SOPs
contracts
manuals
product docs
internal wiki
training material

This is where retrieval/RAG applies.

For the first implementation, I would use PostgreSQL + pgvector rather than introducing a dedicated vector database.

Working memory

Persistent state for an ongoing task:

task objective
requirements
decisions made
files created
open questions
completed steps
human approvals

This should live as explicit versioned artifacts, not buried inside a gigantic chat context.

Example:

/tasks/991/
    task.json
    requirements.md
    evidence.json
    decisions.md
    draft-v1.md
    corrections.json

Experience memory

Everything the AI attempted:

trajectories
tool usage
retrieval
outputs
human corrections
failures
business outcomes

This is the trajectory lake.

Learned memory

What eventually becomes encoded into:

prompts
routing rules
tool policies
LoRA adapters
fine-tuned weights
rubrics
verifiers

Keeping those five separated prevents a lot of architectural confusion.

4. The trajectory becomes the primary data object

Every meaningful job gets one trace_id.

A minimal production trajectory should contain something like:

  "router": {
    "selected": "contract-specialist-v3",
    "confidence": 0.93
  },

  "model": {
    "base": "model-id",
    "adapter": "contract-v7",
    "prompt_version": "12"
  },

  "retrieval": [
    {
      "document_id": "...",

  ],

  "tool_calls": [
    {
      "tool": "contracts.search",
      "version": "2",

    }

  "output": "...",

    "passed": true,

Store big or sensitive payloads elsewhere and reference them from the trace.

I would use:

PostgreSQL
    metadata / relationships / outcomes

MinIO or S3
    encrypted prompts
    retrieved source material
    generated artifacts
    corrected artifacts
    datasets
    adapters

Parquet
    immutable dataset snapshots
    analytical exports

And:

OpenTelemetry
      ↓
Langfuse

for operator-facing observability.

Langfuse should be a view into the system.

It should not be the sole canonical datastore.

5. The Discovery Controller is the key new component

When something goes wrong:

BAD OUTPUT
    ↓
Why?

Do not immediately create a training example.

The controller should classify competing explanations:

ROUTING_FAILURE
RETRIEVAL_FAILURE
MISSING_KNOWLEDGE
STALE_DATA
TOOL_FAILURE
TOOL_SCHEMA_FAILURE
PERMISSION_FAILURE
PROMPT_FAILURE
MODEL_REASONING_FAILURE
MODEL_CAPABILITY_FAILURE
BAD_RUBRIC
NOVEL_TASK
UNKNOWN

Then ask:

What’s the cheapest experiment that distinguishes between these explanations?

Example:

Employee says contract answer is wrong.

Hypothesis 1:
model misunderstood contract.

Hypothesis 2:
retrieval missed an amendment.

Hypothesis 3:
CRM has stale renewal date.

Hypothesis 4:
document parser extracted the date incorrectly.

Potential experiments:

rerun retrieval with known document ID

query authoritative contract DB

inspect extracted document structure

give identical evidence to stronger model

ask employee for canonical answer

Only if the evidence indicates model behavior/capability should training become the preferred fix.

This prevents the system from literally training itself to compensate for broken infrastructure.

6. Prioritized learning instead of “train on everything”

Once an example is training-worthy, don’t sample everything uniformly.

Each domain gets state such as:

task family
success EMA
failure severity
uncertainty
novelty
business value
staleness
training coverage
last trained
label quality

A conceptual priority score:

learning_priority
 =
 failure_severity
 + uncertainty
 + novelty
 + staleness
 + business_value
 - labeling_cost

With a little random exploration so “solved” areas don’t disappear forever.

That is the learning scheduler.

7. Initial technology stack

I would deliberately keep v1 boring.

Application layer

Python
FastAPI
Pydantic
SQLAlchemy

Avoid a heavyweight agent framework initially.

Business workflows should be explicit state machines.

class TaskState:
    trace_id
    user
    permissions
    task_type
    route
    evidence
    tool_results
    candidate_output
    verification
    approval
    outcome

Flow:

classify
→ authorize
→ retrieve
→ route
→ generate
→ verify
→ execute if allowed
→ capture outcome

Local inference

On your machine:

llama.cpp

as the primary controlled runtime.

Ollama remains useful for quick experimentation.

Both should sit behind your own model gateway:

Company App
     ↓
Model Gateway
     ├── local llama.cpp
     ├── cloud vLLM
     └── hosted frontier API

Nothing in the business logic should care where the model physically lives.

Storage

PostgreSQL
pgvector
MinIO

That’s enough initially.

No Pinecone/Milvus/Weaviate/etc. unless scale gives us an actual reason.

Observability

OpenTelemetry
     ↓
Langfuse

Plus your canonical trajectory tables.

Training

Hugging Face Transformers
PEFT
TRL
Unsloth

Unsloth is particularly attractive for QLoRA work on the RTX 5080 laptop.

Cloud inference

When local hardware isn’t sufficient:

vLLM

on a rented GPU.

The application still sees an OpenAI-compatible endpoint.

8. Initial model strategy

Do not start with eight models.

Start with three logical intelligence tiers.

Tier 1
tiny router / classifier

Tier 2
main local specialist

Tier 3
strong escalation model

Working candidates:

Router

Qwen3 ~1.7B–4B class

or another strong current small classifier.

Main local worker

Test:

Qwen3 8B
Gemma-class ~12B
Qwen3 14B

quantized.

With your RTX 5080 Laptop GPU and 64 GB system RAM, the 4B–14B range is where I’d concentrate local experiments.

Strong planner

Initially use a hosted frontier-class model.

Its job is not to answer every question.

It handles:

novel tasks
complex decomposition
ambiguous planning
failure analysis
difficult escalations
dataset/eval generation

As usage data accumulates, we’ll learn which pieces can be pushed downward into cheaper specialists.

9. Specialization ladder

Before training anything:

Can we fix it with a better tool?
        ↓ no

Can we fix retrieval/context?
        ↓ no

Can we improve output schema/verifier?
        ↓ no

Can prompting solve it reliably?
        ↓ no

Does LoRA improve held-out performance?
        ↓ no

Try larger adapter / stronger base.
        ↓

Only then consider full fine-tuning.

The first actual post-training method should therefore be:

SFT + QLoRA on human-verified corrections.

Not RL.

Not SDPO.

Not autonomous continual training.

10. Evaluation becomes a first-class product

Every specialist must have an eval suite before we train it.

Hierarchy of evidence:

actual business outcome
        >
deterministic execution/test
        >
domain expert rubric
        >
calibrated model judge
        >
generic LLM preference

For example:

SQL agent:

execute against sandbox
compare result

Extraction:

schema validation
field-level exact/fuzzy match

Contract analysis:

canonical dates
source citations
clause identification
human rubric

Coding:

tests
lint
security scan

Do not ask an LLM judge to evaluate something we can objectively test.

11. Intelligence-density becomes the platform KPI

The goal isn’t:

lowest token cost

or:

highest benchmark score

It is something closer to:

business value × successful outcomes
─────────────────────────────────────
inference + tools + latency + human work

Track at minimum:

task success rate
acceptance rate
human correction rate
escalation rate
cost per successful task
latency per successful task
tokens per successful task
success by specialist
success by model
success by adapter
success by workflow
success by tool

This is how we’ll know when a 4B specialist genuinely beats a much larger model economically.

12. Implementation phases

I would build in this order.

Phase 0 — Choose one vertical slice

Pick one real business workflow meeting these criteria:

high value
repeated often
reasonably measurable
has accessible data
human currently performs it
mistakes aren’t catastrophic
ideally read-only

Examples:

contract renewal analysis
invoice normalization
sales-account research
support-ticket classification
document compliance review
CRM enrichment

Don’t start with “general company assistant.”

Phase 1 — Instrumented single-model workflow

Build:

authentication
one workflow
one model
retrieval if needed
2–5 tools
structured output
verification
full trajectories

No model training.

No multi-agent system.

No smart router.

Exit condition

For almost every request, we can reconstruct:

who asked
what was requested
what context was supplied
what tools ran
what model version ran
what it returned
what the employee changed
whether it succeeded
what it cost

This foundation matters more than model sophistication.

Phase 2 — Build the eval suite

From real examples, create:

gold cases
failure cases
edge cases
security cases
tool-error cases
retrieval cases

Version it:

contract-eval-v1
contract-eval-v2
...

Every code/model/prompt change runs against it.

Now we have a scientific baseline.

Phase 3 — Correction capture

Make feedback almost invisible.

Employee sees AI draft.

They:

accept
edit
reject

We preserve:

AI artifact
employee artifact
diff
trajectory
reason where available
eventual outcome

This produces extremely valuable company-specific supervision.

Phase 4 — First specialist adapter

Now train our first QLoRA.

Dataset:

verified successful examples
+
human-corrected failures

Hold out a meaningful portion.

Then compare:

prompt-only incumbent
vs
LoRA candidate

on the frozen eval suite.

If LoRA doesn’t clearly help:

don’t deploy it.

Phase 5 — Router + multiple specialists

Only now introduce logical specialists.

request
    ↓
router
 ┌──┼──┐
 ↓  ↓  ↓
A   B   C
     │
 difficult?
     ↓
strong planner

Initially the specialists may simply be:

same base model
+
different adapters
+
different tools/prompts

This greatly simplifies serving.

Phase 6 — Discovery Controller

Implement failure diagnosis.

Every failure enters:

failure queue

Controller assigns:

probable cause
confidence
business severity
recommended experiment
recommended owner

Example:

{
  "trace": "abc123",
  "likely_failure": "retrieval_failure",
  "confidence": 0.74,

  "alternatives": [
    "model_reasoning_failure",
    "stale_source"
  ],

  "recommended_test":
    "retrieve known amendment directly and replay",

  "training_recommended": false
}

This is where the system starts becoming genuinely adaptive.

Phase 7 — Prioritized replay

Introduce:

domain performance
uncertainty
novelty
staleness
business value

Now your dataset-generation process becomes intelligent rather than FIFO.

Phase 8 — Candidate factory

Automate:

dataset snapshot
        ↓
training job
        ↓
model/adapter manifest
        ↓
offline eval
        ↓
comparison report
        ↓
shadow
        ↓
canary
        ↓
promotion

But deployment remains gated.

This is the real self-improvement factory.

Phase 9 — Advanced learning experiments

Only after the previous system has accumulated significant high-quality production experience:

Explore:

DPO / preference optimization
GRPO-style RL
SDPO
automated curriculum generation
teacher/student distillation
active learning
Model-Discovery-style experiment selection

Those should compete against the simpler QLoRA baseline.

Not automatically replace it.

13. What I would deliberately NOT build yet

This is almost as important as the architecture.

Don’t initially build:

❌ Kubernetes

❌ a complicated multi-agent framework

❌ ten specialized models

❌ full fine-tunes

❌ autonomous RL

❌ SDPO production loop

❌ dedicated vector database cluster

❌ giant knowledge graph

❌ model that rewrites itself

❌ agent-generated production code deployed automatically

❌ separate GPU instance for every specialist

❌ elaborate MCP mesh

❌ sophisticated Bayesian MDA implementation

A strong model with explicit failure hypotheses and controlled experiments will get us surprisingly far.

16. The first thing I would implement

Before downloading a pile of models, I’d create these six pieces:

1. Task schema

2. Specialist schema

3. Tool schema

4. Trajectory schema

5. Model gateway

6. Evaluation runner

Then implement one real company workflow end to end.

That means the very first milestone isn’t:

“Run Qwen locally.”

It’s:

“Run one real company task end-to-end and capture enough evidence that we can explain exactly why it succeeded or failed.”

That distinction should guide the entire project.

The resulting north-star architecture

Everything in the architecture collapses cleanly into this:

EXECUTION
models + tools + context + workflows
               │
               ▼
          EXPERIENCE
complete production trajectories
               │
               ▼
           DISCOVERY
why did this succeed/fail?
what evidence do we need next?
               │
               ▼
         IMPROVEMENT
fix system or train specialist
               │
               ▼
          EVALUATION
prove it is actually better
               │
               ▼
           RELEASE
shadow → canary → champion
               │
               └───────────────┐
                               ▼
                            EXECUTION

The models are replaceable workers. The compounding company asset is: task ontology + tools + permissions + company knowledge + persistent artifacts + trajectories + corrections + outcomes + evals + discovery logic + dataset lineage. That’s the system I would build.
