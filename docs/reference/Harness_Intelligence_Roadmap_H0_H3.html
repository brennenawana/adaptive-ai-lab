Harness Intelligence Roadmap — H0–H3

Treat the developer-agent harness as a first-class part of intelligence: benchmark it, continuously optimize how fixed harnesses use their native capabilities, optionally test dynamic capability synthesis where permitted, promote proven workflows/capabilities under control, and eventually route tasks within explicit user/company constraints.

Status: Strategic roadmap — not current FIS execution scope Dependency: D0 telemetry first Core rule: ephemeral autonomy, controlled persistence

1. Executive summary

The project has reached the point where “which model?” is too narrow a question. Real agent capability comes from the combination of model, harness, context, tools, policies, subagents, verification, and—in newer systems—the ability to create capabilities during the trajectory.

Desired end state A company intelligence platform that learns which execution system—model + harness + capability graph + context policy + verifier—best solves each task, and can safely synthesize missing capabilities when the existing graph is insufficient.

The H0–H3 program develops that idea in four stages:

StageQuestionPrimary output
H0How much capability comes from the harness versus the model?Controlled harness benchmark
H1How can the harness configuration itself improve over time?Static workflow optimization + optional dynamic capability experiments
H2Which successful workflows/capabilities deserve to become durable platform assets?Capability & workflow promotion pipeline
H3Can the system learn the best allowed execution configuration for each task?Constrained execution-system router

H1 has two explicit branches. H1-S improves a fixed harness such as Claude Code by learning better skills, hooks, subagents, model/effort assignments, MCP/plugin bundles, context rules, verification workflows, and orchestration policies. H1-D studies dynamic capability synthesis where the harness and security policy permit it. DeepSeek Harness is especially important to H1-D because its opt-in self-referential Cordis toolset allows a running model to inspect the harness and mount temporary in-memory plugins that can add tools, listeners, or services during the session. Those temporary capabilities remain ephemeral and are not automatically promoted to permanent configuration.

This changes the optimization target from:

Cost remains one dimension, but not necessarily the dominant one. Other dimensions include correctness, reliability, latency, autonomy, human attention, security, reproducibility, and capability reuse.

Core architectural principle The system may autonomously create an ephemeral candidate capability. It may not autonomously convert that capability into a durable trusted platform primitive.

3. Relationship to FIS and D0

FIS

FIS is the business-task laboratory. It teaches how to build trustworthy evals, separate model failures from system failures, capture trajectories, compare specialists, and learn routing decisions.

D0 — Developer Agent Telemetry

D0 is the observation substrate for developer-agent work. It normalizes Claude Code, Codex, Cursor, and future harnesses into a common record of tasks, sessions, tools, models, Git state, verification, rework, latency, tokens, and outcomes.

H0–H3

H0–H3 is the experimental harness-intelligence track built on top of D0. It supports both fixed-harness optimization and dynamic-harness experimentation; switching harnesses is never a prerequisite.

FIS
  → teaches trustworthy system evaluation

D0
  → captures comparable developer-agent trajectories

H0
  → measures harness / execution-system contribution

H1-S
  → learns better use of a fixed harness

H1-D
  → measures self-generated capability contribution

H2
  → promotes useful workflows/capabilities into reviewed assets

H3
  → routes within the allowed execution envelope

The two tracks eventually converge on the same platform primitives: trajectories, canonical outcomes, feature snapshots, routers, candidate registries, eval gates, and promotion decisions.

5. H0 — Controlled harness benchmark

Question How much of verified developer-agent performance is attributable to the harness rather than the base model?

Goal

Establish a scientifically credible baseline across Claude Code, Codex, Cursor, DeepSeek Harness, and future harnesses without collapsing model and harness differences into one comparison.

Preferred experiment designs

A. Same-model cross-harness experiment

When the same exact model/provider configuration can be used across multiple harnesses:

same task
same repo snapshot
same completion condition
same model
same reasoning setting
same external services where possible

Harness A
vs
Harness B
vs
Harness C

This is the cleanest estimate of harness effect.

B. Harness-native system benchmark

When exact model equality is impossible or artificial, compare each harness using its realistic best production configuration, but label the result correctly as an execution-system comparison, not a pure harness comparison.

Task corpus

Use a versioned software-engineering task suite with objective or strongly verifiable outcomes, for example:

  • focused bug fixes;
  • test failures with known causes;
  • small feature implementations;
  • repo-wide refactors;
  • architecture/research tasks with artifact acceptance criteria;
  • long autonomous experiment tasks;
  • interactive IDE/UI tasks where applicable.

Tasks should be stratified by type. “Claude beats Codex” is less useful than “Harness X is better for long autonomous repo work while Harness Y is better for focused patches.”

Controls

  • same repository commit/worktree;
  • same task wording and declared completion criteria;
  • same test/eval commands;
  • fixed permission/sandbox envelope where meaningful;
  • record exact model and harness versions;
  • do not allow one harness access to hidden evaluation truth unavailable to another;
  • separate interactive developer attention from autonomous wall time.

Required H0 outputs

  • verified success by task class;
  • major rework / repair / revert rate;
  • developer attention per successful task;
  • wall time;
  • tool-call patterns and tool failures;
  • token/compute/cost where observable;
  • context compactions / subagents / retries;
  • model-versus-harness controlled comparisons where possible.

H0 completion condition

H0 succeeds when there is enough controlled evidence to identify meaningful harness effects for at least several task classes without pretending observational usage data is causal.

Question How can an agent harness become more effective over time, whether the harness is fixed by policy or dynamically extensible?

H1-S — Static harness learning

Fixed harness does not mean fixed behavior. If a developer is required to use Claude Code, H1-S optimizes the configuration and workflow inside Claude Code rather than trying to move the developer to another harness.

H1-D — Dynamic capability synthesis

Question Where permitted, does allowing the running model to create temporary harness capabilities improve verified task outcomes enough to justify the added complexity and risk?

DeepSeek Harness provides a concrete mechanism for this experiment. Its architecture treats major components as plugins, and its opt-in self-referential Cordis toolset can inspect the current runtime and mount temporary plugins that add capabilities during the session.

Primary controlled experiment

same model
same task corpus
same DeepSeek Harness version/profile
same initial tools
same context
same evaluator

H1-D control
  dynamic capability synthesis OFF

vs

H1-D treatment
  dynamic capability synthesis ON

Treatment behavior

The agent may:

  • inspect the live harness;
  • identify a missing capability;
  • write temporary capability/plugin code;
  • mount it;
  • use it in later steps;
  • unmount it;
  • leave a durable trajectory record of the mutation.

The agent may not automatically promote the temporary capability into durable trusted configuration.

Tasks likely to reveal value

  • large structured-log investigations;
  • repeated transformations where shell one-liners are inefficient;
  • custom repository queries;
  • specialized static-analysis needs;
  • multi-source evidence aggregation;
  • repetitive API/tool choreography;
  • tasks where the missing abstraction only becomes obvious during execution.

H1 completion condition

H1 succeeds when at least one harness configuration can be shown to improve through controlled workflow/capability changes. Dynamic synthesis is not required. A company may complete H1 entirely through H1-S if its execution envelope prohibits harness mutation.

7. H2 — Capability & Workflow Promotion

Question When does a successful harness improvement—whether discovered statically or generated dynamically—deserve to become a durable, reviewed platform asset?

H2 turns repeated workflow and capability discoveries into controlled organizational learning. Inputs may come from H1-S (skills, hooks, subagent profiles, orchestration rules, context policies, verifier workflows) or H1-D (ephemeral generated tools/services/plugins).

successful workflow / ephemeral capability
      ↓
trajectory evidence
      ↓
repeated useful pattern?
      │
    no ───→ expire / retain as local experiment
      │
     yes
      ↓
candidate harness asset
      ↓
canonical implementation
      ↓
deterministic tests
      ↓
security / permission review
      ↓
benchmark evaluation
      ↓
shadow / limited use
      ↓
PROMOTE or REJECT

Important distinction

The system does not blindly preserve model-written temporary source. Promotion should normally synthesize a canonical reviewed implementation from the observed need and behavior.

Candidate evidence

A promotion candidate may be triggered when a capability pattern:

  • appears independently across multiple successful trajectories;
  • solves a recurring task family;
  • has measurable positive outcome/attention effects;
  • reduces repeated shell/tool choreography;
  • has stable semantics that can be tested deterministically;
  • fits an approved permission boundary.

Promotion gates

  1. Need gate: recurring evidence demonstrates a real missing abstraction.
  2. Correctness gate: deterministic tests and contract tests pass.
  3. Security gate: permissions and data access are explicit and least-privilege.
  4. Evaluation gate: candidate improves a held-out task suite or at least does not regress it.
  5. Operational gate: logging, versioning, rollback, failure behavior and compatibility are acceptable.
  6. Human approval gate: durable production promotion is reviewed.

H2 completion condition

H2 succeeds when the system can demonstrate at least one end-to-end transition from recurring trajectory evidence to a reviewed, versioned, durable harness asset with preserved lineage and rollback. The first promoted asset may be a skill, hook, orchestration policy, verifier, plugin/tool, or another workflow primitive.

Example routing targets

focused patch
  → Codex + coding model + shell/edit/test profile

H3 oracle

Before training a router, compute a cheapest/lowest-burden sufficient-system oracle on held-out tasks:

for each task:
  identify every execution system that succeeds
  choose the sufficient system under the declared objective:
    quality constraint first
    then developer attention
    then latency / cost / resource burden as configured

Router input boundary

As in FIS R5, H3 must use only signals available at the routing point. Hidden evaluator outcomes may supervise training labels but never enter production features.

H3 metrics

  • verified success;
  • distance to execution-system oracle;
  • developer attention per success;
  • unnecessary escalation to expensive/complex systems;
  • routing regret;
  • latency;
  • compute and monetary cost;
  • capability-mutation frequency;
  • rework/revert rate;
  • security/policy violations.

H3 completion condition

H3 succeeds when a learned or deterministic execution-system policy outperforms a reasonable static default on held-out tasks without relying on evaluator leakage or unacceptable operational complexity.

10. Security and governance

Static harness optimization and dynamic harness mutation have different risk classes. H1-S should remain within approved harness extension mechanisms and organization policy; H1-D adds a higher-risk runtime mutation surface requiring stronger isolation.

Required boundaries

  • Ephemeral mutations run in isolated development/sandbox environments first.
  • No production secrets or unrestricted credentials in H1 experiments.
  • Mutation source and capability-set changes must be logged.
  • Generated capability code must not directly modify benchmark truth/evaluator state.
  • Mutation policy should restrict which services/capabilities are exposed.
  • Network, shell, filesystem, subprocess, and credential permissions should be explicit.
  • Promotion is separate from runtime mutation.
  • Durable promotion requires tests, policy review, versioning, and rollback.
  • Production harnesses should fail closed when capability/config digests do not match approved profiles.

Trust levels

LevelMeaningExample
0Static approved harnessFixed Claude Code/Codex profile
1Ephemeral capability synthesis in disposable sandboxDeepSeek temporary Cordis plugin
2Reviewed experimental capability profileCandidate plugin enabled only in benchmark/shadow
3Approved durable capabilityVersioned production tool/plugin
Self-improvement ≠ uncontrolled self-modification. The runtime may explore. Durable system change must pass a separate evidence and governance pipeline.

12. Recommended sequence and dependencies

D0

Observe first

Instrument Claude Code, Codex, Cursor, and later DeepSeek Harness. Establish common task/session/outcome telemetry. Do not make comparative claims until outcome data is trustworthy.

H0

Benchmark harnesses

Run controlled same-model experiments where possible and execution-system comparisons where exact model equality is impossible.

H1-S

Optimize fixed harnesses

Learn better skills, hooks, subagent profiles, model/effort assignments, context policies, plugin/MCP bundles, verification workflows, and orchestration rules inside approved harnesses.

H1-D

Optionally test dynamic capability synthesis

Where policy permits, use DeepSeek Harness as the first concrete static-vs-self-extending experiment. Keep dynamic capabilities ephemeral.

H2

Learn durable workflow/capability assets

Promote useful recurring skills, hooks, orchestration policies, verifiers, tools, and other harness assets through one governed pipeline.

H3

Route within execution envelopes

Learn the best allowed model + harness/profile + workflow assets + mutation policy for each task. A fixed-harness organization simply constrains the search space.

Relationship to current FIS roadmap

H0–H3 should not interrupt the immediate FIS routing work. The recommended parallel progression is:

R5 learned silent-failure routing
  → R6 multi-tier model routing
  → later specialization / continual learning

Harness track:

  → H0 harness benchmark
  → H1-S fixed-harness workflow optimization
  → optional H1-D dynamic capability synthesis
  → H2 workflow/capability promotion
  → H3 constrained execution-system routing

Convergence:
shared trajectory/eval/router/promotion platform

13. Program-level acceptance criteria

  • D0 provides provider-neutral task/session/outcome telemetry before H0 comparative claims.
  • H0 distinguishes same-model harness effects from harness-native execution-system effects.
  • H1-S can improve a fixed harness without requiring harness switching or dynamic mutation.
  • H1-S experiments version and evaluate skills, hooks, subagent/orchestration policies, context rules, plugins/MCP profiles, and verifiers where applicable.
  • H1-D, when used, employs a controlled static-vs-dynamic design with mutation telemetry.
  • Dynamic capabilities remain ephemeral and isolated during H1-D.
  • H2 promotion preserves complete lineage from originating trajectories/mutations to durable workflow or capability assets.
  • No model-written temporary plugin is automatically treated as production-ready source.
  • Durable capabilities pass correctness, security, evaluation, operational, and human-review gates.
  • H3 respects an explicit execution envelope; hard user/company harness constraints are never treated as optimization failures.
  • H3 router inputs are production-observable only.
  • H3 is compared to static baselines and an execution-system oracle.
  • All model, harness, profile, capability, mutation, evaluator, and outcome versions are traceable.
  • The program can accept negative results instead of forcing every stage to “succeed.”

14. Open research questions

  • How much can a fixed harness improve purely through better skills, hooks, context, subagent policy, and orchestration?
  • Which harness workflow assets transfer across repositories versus needing project-specific versions?
  • When should repeated instructions move from always-on context into an on-demand skill?
  • How should model/effort selection be learned within one harness?
  • How much of coding-agent performance variance is model versus harness?
  • Which task classes benefit most from dynamic capability synthesis?
  • How often do models create unnecessary tools because capability generation itself is attractive?
  • Can capability mutations be represented semantically enough to cluster equivalent inventions?
  • When should a recurring temporary capability become a skill, tool, MCP server, hook, or native harness plugin?
  • Should a router choose a harness before model selection, model before harness, or the tuple jointly?
  • Can post-execution failure predictors learned in FIS transfer to developer-agent routing?
  • How should developer attention be measured without turning D0 into surveillance?
  • What is the correct security boundary for self-extending enterprise harnesses?
  • When is weight training actually more economical than teaching the harness a new capability?
