WHY SUITE v3 EXISTS

The following benchmark/harness issues were discovered independently during prior model experiments and deliberately deferred instead of being patched mid-baseline.

Suite v3 must address exactly these known classes of issues, subject to reconciliation with the repo documentation:

1. BACKGROUND SETTLEMENT REALISM

Background settlements are not posted to the ledger in 7 of 12 classes.

This created worlds where compound-failure interpretations by the frontier could be defensible even when the scenario's intended diagnosis expected only the injected defect.

Suite v3 should make settlement/background ledger state realistic and internally consistent.

Do not simply modify expected answers.
Fix the generated world and its invariants.

2. S08 AMOUNT-vs-BALANCE REALISM

There is a known S08 realism issue involving amount versus balance semantics.

Inspect the exact documented defect before changing code.

Fix the simulator/world semantics first.

Then update any deterministic expected evidence/scoring implications that legitimately follow from the corrected world.

Do not change the rubric merely because a model preferred another explanation.

3. FORBIDDEN-CLAIM / REFUTATION FALSE POSITIVES

The scorer previously counted some refutations as assertions.

Suite v3 should implement the documented refutation-cue lookback / polarity behavior so assertions and explicit refutations are distinguished robustly.

This must be covered by targeted scorer tests.

Do not make the scorer generally permissive.

4. IDEMPOTENCY-KEY OBSERVABILITY / VERIFIER GAP

The current verifier has a gap around idempotency keys.

The Suite v3 backlog describes idempotency_key as an observed identifier.

Inspect the exact current semantics and implement the smallest model-neutral correction so the verifier evaluates claims against evidence that the agent could actually observe.

The rule must not introduce gold-data leakage.

Add explicit gold-leak tests.

GENERATION-BUDGET POLICY

R3b closed the token-budget experiment.

For Suite v3, use operationally justified, pre-registered per-arm budgets rather than reopening model tuning.

Recommended default unless current repo documentation has a stronger already-recorded policy:

Qwen:
max_tokens = 4096

Reason:
Qwen completed the suite at 4096; R3b showed only one budget-sensitive Qwen case and no broad cap problem. 4096 is the lower-latency incumbent operating envelope.

Nemotron:
max_tokens = 8192

Reason:
R3b showed 4096 materially truncated Nemotron reasoning. 8192 is the minimum investigated envelope that removes most of that artificial truncation.

Frontier:
use the existing frozen frontier configuration/budget from the current benchmark harness, sufficient to avoid known output truncation.

These are SYSTEM-CANDIDATE operating configurations, not a pure parameter-equality model benchmark.

If you believe a different budget policy is required, document and commit the rationale BEFORE any Suite v3 model run. Do not decide after seeing scores.

- TEST all scenarios reachable

RELEASE GATE — DETERMINISM

Regenerate the same Suite v3 corpus at least twice under the same seed/config and verify the canonical world/evidence identifiers are stable according to existing determinism rules.

RELEASE GATE — SCENARIO INVARIANTS

For each scenario family, validate deterministic world invariants independent of model output.

At minimum include:
- injected defect exists
- required background state exists
- evidence needed for diagnosis is reachable
- distractors remain plausible but not contradictory
- expected ledger/event ordering relationships hold
- model-facing identifiers correspond to generated entities
- no unexpected second defect is accidentally introduced by the generator
