Initial Architecture & Implementation Plan

Developer Agent Telemetry D0

A provider-neutral telemetry plane for observing, evaluating, and eventually improving AI-assisted software development across Claude Code, Codex, Cursor, and future developer agents.

Status: Planned — not in current FIS execution scopeInitial user: single developerPrimary mode: local-first telemetryRaw prompts/code: off by default

1. Executive summary

D0 creates a durable, vendor-neutral record of how developer agents are used and whether their work actually succeeds. The first objective is observability, not automation.

Working definitionObserve, evaluate, and improve AI-assisted software development.

Claude Code, Codex, Cursor, and future coding agents expose different telemetry surfaces. D0 normalizes those surfaces into a single developer-agent trajectory model owned by the project. It then correlates agent activity with independent engineering outcomes such as tests, commits, reverts, review, and task completion.

D0 deliberately avoids declaring a developer “productive” based on token volume, lines changed, or agent usage. Those are inputs. The outcome layer is separate and must be grounded in evidence.

North-star question

For this class of engineering work,
which agent / model / workflow produces
the most reliable verified outcome
with the least developer intervention?

Cost is one optimization dimension alongside correctness, rework, latency, autonomy, reliability, and developer attention. It is not assumed to be the dominant objective.

2. Design principles

Outcome-first

Token counts and tool calls describe activity. Tests, accepted commits, rework, and retained changes describe outcomes.

Provider-neutral

Claude, Codex, and Cursor are adapters. The canonical schema, IDs, outcome logic, and historical record are ours.

Privacy-minimizing

Do not collect raw prompts, source code, or full responses by default. Begin with metadata and explicit outcome signals.

Correlation, not surveillance

The initial system exists to understand developer-agent workflows, not to rank developers or create hidden performance scores.

Experiment lineage

Record tool version, model, repository, session, task, branch, commit, tests, and outcome so claims can be reproduced.

Progressive instrumentation

Start with coarse, trustworthy events. Add richer content only when a specific question requires it and policy permits it.

D0 is not an employee scoring system.The schema may include a developer identifier for correlation, but D0 should not produce leaderboard-style productivity judgments. Multi-developer governance belongs to a later phase with explicit policy and consent.

3. Scope & non-goals

In scope for D0

  • Capture local Claude Code telemetry through OpenTelemetry.
  • Capture Codex telemetry through its OpenTelemetry configuration.
  • Probe the installed Cursor version/plan for supported hooks or structured agent-export surfaces.
  • Normalize agent events into one canonical schema.
  • Correlate sessions with repository, branch, commit, diff metadata, tests, and task outcome.
  • Build a personal dashboard for one developer across multiple coding agents.
  • Measure verified task outcomes, rework, failure patterns, autonomy, latency, and optional cost.
  • Preserve enough lineage to support future cross-agent experiments.

Explicitly out of scope

  • Automatically routing coding tasks between agents.
  • Automatically changing prompts/rules based on telemetry.
  • Team-wide monitoring or employee performance scoring.
  • Capturing raw prompts, full source code, or full responses by default.
  • Replacing Git, CI, issue trackers, or vendor-native admin analytics.
  • Claiming causal productivity improvement from observational data alone.
  • Changing FIS implementation work to accommodate D0.

6. Canonical data model

D0 should model developer work at three levels rather than treating every tool event as a “trajectory.”

Developer task

The human intent: “implement R3b,” “fix CI,” “refactor auth,” “write migration.” This is the unit that eventually receives an outcome.

Agent session

A Claude/Codex/Cursor conversation or run used to advance the task.

Agent event

Tool call, model request, error, permission decision, test invocation, edit event, or other low-level telemetry.

Core entities

developer_task
  ├── 1..N agent_session
  │       └── 1..N agent_event
  ├── 0..N git_commit
  ├── 0..N verification_run
  ├── 0..N human_intervention
  └── 1 task_outcome

Key distinctionThe agent event stream describes what happened. The task outcome describes whether it was useful. Never infer the latter directly from token volume, lines changed, or the agent's own claim of completion.

7. Correlation & outcome strategy

Correlation hierarchy

  1. Explicit task ID — preferred. A task is opened before a substantial agent session.
  2. Native agent session ID — mapped to the task at session start.
  3. Git branch / worktree — useful secondary scope.
  4. Commit hashes — durable evidence that work crossed a boundary.
  5. Test runs — correlated by repository, branch, commit, and time window.
  6. Manual annotation — used when automation cannot distinguish intent.

Outcome hierarchy

production / real-world outcome
        >
merged / retained change
        >
objective automated verification
        >
review acceptance
        >
developer acceptance
        >
agent self-report

Initial task completion rule

Verified successful taskA task is successful when its declared completion condition is met and at least one independent verification signal supports it. Examples: targeted tests pass; requested artifact exists and is accepted; a fix remains in the repository after review.

Rework window

D0 should support a configurable observation window after completion—for example, 24 hours or the next related commit—to detect immediate reverts, repair commits, or major manual rewrite. This is more informative than measuring whether an agent produced code.

Derived metrics for later analysis

agent_effectiveness =
  verified_successes / developer_attention

reliability =
  verified_successes / completed_tasks

autonomy =
  1 - (human_active_time / task_wall_time)

rework_burden =
  major_rework_tasks / successful_tasks

optional_intelligence_density =
  weighted_verified_outcome /

Do not optimize lines of code.LOC, tokens, and tool calls are diagnostic variables. They should not become target metrics because agents can trivially increase them without improving outcomes.

9. Privacy & security

D0 default collection policy

DataDefaultReason
Session/task IDsCollectRequired for correlation
Model / harness / versionCollectRequired for reproducibility
Token counts / timingCollectOperational metrics
Tool names + result statusCollectWorkflow analysis
Git commit / branch metadataCollectOutcome lineage
Test names/counts/resultsCollect carefullyVerification evidence
Raw promptsDo not collectHigh sensitivity; not needed for D0
Tool arguments / source contentsDo not collectMay contain code, secrets, customer data
Full model responsesDo not collectNot needed for initial questions
Environment variables / secretsNever collectSecurity boundary

Data handling rules

  • Filter/redact at the collector before persistence when possible.
  • Store provider-native payloads only when necessary for adapter debugging, with short retention.
  • Canonical normalized records should contain the minimum durable fields.
  • Separate personal experiments from company/client telemetry by repository and policy boundary.
  • Do not reuse employer source code, prompts, telemetry, or private work in external demos without authorization.
  • Before D0 becomes multi-developer, create an explicit governance and disclosure policy.

10. Initial technology stack

D0 should be intentionally small and portable.

ComponentInitial choiceRole
Telemetry transportOpenTelemetry CollectorReceive, filter, redact, and forward
Canonical databasePostgreSQLTasks, sessions, events, outcomes, correlations
Raw/debug retentionLocal filesystem or object storage, optionalShort-lived adapter debugging only
NormalizerSmall Python service / workerMap provider events to canonical records

Verification ingestionWrapper / test-result parserTest and validation outcomes
DashboardSimple app or lightweight BI viewPersonal visibility; replaceable

Why Postgres instead of an observability vendor as the authority?

Vendor observability tools are useful views, but the durable asset is the correlation between developer task, agent sessions, model/harness versions, commits, verification, and outcomes. That relationship should remain queryable even if the dashboard or agent vendor changes.

12. D0 implementation phases

D0.0

Capability probe & experiment contract

Inventory exact installed Claude Code, Codex, and Cursor versions and determine what each exposes without raw-content capture.

  • Record subscription/client context.
  • Build capability manifests.
  • Define privacy defaults.
  • Freeze canonical IDs and initial schema.

Exit: no adapter implementation assumptions remain undocumented.

D0.1

Collector + canonical store

  • Launch local OTel Collector.
  • Create Postgres schema.
  • Create normalizer API/worker.
  • Implement redaction tests.
  • Create a simple doctor command showing telemetry health.

Exit: synthetic events survive collector → normalizer → Postgres with lineage intact.

D0.2

Claude Code adapter

Start with Claude Code because its OTel monitoring surface is explicit and rich.

  • Enable telemetry to the local collector.
  • Keep user prompts and tool details disabled.
  • Normalize session/model/token/tool/timing events.
  • Run three known tasks and reconcile counts manually.

Exit: three sessions can be reconstructed from canonical records without raw prompt/code capture.

D0.3

Codex adapter

  • Configure Codex OTLP export.
  • Normalize to the same session/event schema.
  • Record Codex version and telemetry-schema capability.
  • Run equivalent known tasks where practical.

Exit: Claude and Codex sessions can be queried from the same tables without provider-specific dashboard logic.

D0.4

Cursor adapter

  • Probe hooks and structured CLI/export capabilities available to the installed account/version.
  • If hooks are available, emit normalized local events.
  • If not, use the least-invasive documented structured surface.
  • Mark unavailable fields explicitly.

Exit: Cursor activity is represented in the same canonical session model without undocumented scraping.

D0.5

Outcome correlation + personal dashboard

  • Add task start/end workflow.
  • Correlate agent sessions to Git and tests.
  • Add manual rework/acceptance annotation.
  • Build dashboard views defined below.
  • Use D0 personally for several weeks before drawing optimization conclusions.

Exit: at least 20–30 completed tasks have trustworthy outcome records and can be compared across harness/model/task class.

14. Initial personal workflow

Instrumentation should not add enough friction that it changes how work is done.

Recommended task lifecycle

      ↓
task_id exported to shell / local context
      ↓
Claude Code / Codex / Cursor sessions occur normally
      ↓
Git + tests + agent telemetry accumulate
      ↓
end-task --status complete
      ↓
automatic enrichment
      ↓
short human annotation:
  accepted?
  rework?
  goal achieved?
      ↓
task_outcome finalized

Manual annotation should take seconds

Outcome: verified success?     [y/n]
Human rework:                  [none/minor/major]
Follow-up fix required?        [y/n]
Keep this change?              [y/n]
Notes (optional):              [...]

The manual answer is not treated as perfect ground truth; it is one evidence source combined with tests and Git history.

15. D0 acceptance criteria

D0 is complete when the system can support a trustworthy personal baseline, not when every possible agent signal is captured.

  • Claude Code events arrive through OTel without raw prompt/tool content.
  • Codex events arrive through OTel and normalize into the same schema.
  • Cursor capability is probed and a supported adapter path is implemented or its limitation is explicitly documented.
  • Canonical task/session/event/outcome schemas are versioned.
  • Provider-native telemetry versions are recorded.
  • At least one privacy/redaction test fails if prompt/source content would be persisted unexpectedly.
  • Agent sessions can be correlated to repository, branch, and commit where applicable.
  • Tests/verification can be attached independently of the agent's own completion claim.
  • Developer rework can be recorded with minimal friction.
  • The dashboard distinguishes activity metrics from outcome metrics.
  • At least 20–30 real personal tasks are captured before comparative recommendations are made.
  • No automatic agent routing or self-modification is introduced in D0.

17. Future roadmap after D0

D1 — Comparative developer-agent experiments

After sufficient observations exist, run controlled experiments rather than relying only on historical usage.

same task class
same repo constraints
same verification
        ↓
Claude vs Codex vs Cursor/model
        ↓
verified outcomes + rework + attention

D2 — Developer-agent routing

Only after D1 should the system recommend which agent/model to use for a task class.

developer task
      ↓
task classifier
      ↓
recommended harness/model
      ↓
execution
      ↓
verified outcome
      ↓
routing evaluation

Candidate routing signals might include task class, repo/language, expected autonomy, need for browser/UI work, expected duration, and historical success.

D3 — Context / workflow optimization

Compare project instructions, skills, hooks, MCP tools, goal templates, and verification workflows. The unit of optimization becomes the developer-agent system, not the base model alone.

D4 — Multi-developer organization view

Before adding multiple developers, introduce governance: disclosure, access controls, retention, opt-outs, aggregation rules, and explicit prohibition on hidden individual performance scoring.

D5 — Reusable client offering

Package the collector, normalized schema, privacy policy, dashboards, and experiment playbook so a client can instrument its existing AI-development tools before deciding what to standardize or automate.

19. Current implementation references

These references are included so D0 can be revisited against actual tool capabilities at implementation time. Re-check them before building because telemetry surfaces evolve quickly.

  • Claude Code — Monitoring / OpenTelemetry: code.claude.com/docs/en/monitoring-usage. Documents OTel metrics, events/logs, optional traces, identity/session attributes, and privacy defaults such as prompts/tool details not being logged unless explicitly enabled.
  • OpenAI Codex — configuration schema: github.com/openai/codex/.../config.schema.json. The official Codex repository exposes OTel configuration including OTLP HTTP/gRPC exporters and prompt-logging control.
  • Cursor — Hooks: cursor.com/blog/hooks-partners and cursor.com/blog/enterprise. Cursor describes hooks as scripts that can observe/control stages of the agent loop. Availability should be verified for the installed plan/version before D0 assumes them.
  • Cursor CLI — structured/non-interactive usage: docs.cursor.com/en/cli/using. Provides a documented fallback surface including structured output for scripted CLI use.
