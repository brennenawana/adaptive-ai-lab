Fintech Integration Sandbox · R6

Modern Local Specialist Refresh

Refresh the local-model frontier before changing weights. Compare the historical Qwen3-8B control against a modern small Qwen, current Qwen3.8-27B, a separate extreme-efficiency Ternary Bonsai 27B arm, and the established Nemotron challenger under frozen Suite v3.

Primary factor: local execution systemTEST: once per DEV-qualified candidateTraining: out of scope

1. Executive summary

R5 showed that the learned silent-failure routers mostly learned task/template difficulty rather than robust per-answer failure detection. Before QLoRA, R6 asks the cheaper causal question: how much of the residual FIS failure burden disappears if the local specialist is refreshed to modern 2026 models?

Primary outcome. Identify the genuinely non-dominated local operating points by verified quality, silent-failure burden, latency, resource footprint, and marginal case coverage—and use that evidence to choose the next intervention.

R6 is a model-refresh/substrate-selection milestone, not a training or learned-routing milestone. It must leave behind hardened model provenance, a modern small-tier result, a current 27B result, an efficiency result if Bonsai is viable, a pass-set/dominance analysis, and exactly one recommended next milestone.

2. Why R6 now

  • Qwen3-8B is a useful historical control but no longer represents the modern small-Qwen frontier.
  • Nemotron is stronger locally but slow/resource-heavy.
  • R5 did not demonstrate a strong generalized post-answer silent-failure detector.
  • The MSI already holds two current Qwen3.8-27B quants plus a separate Prism Ternary Bonsai 27B artifact.

3. Scientific questions

  1. Can Qwen3.5-9B materially improve the small local tier over Qwen3-8B?
  2. Does Qwen3.8-27B outperform or operationally dominate Nemotron?
  3. How much FIS capability does Ternary Bonsai retain at its much smaller artifact footprint?
  4. Do the models solve complementary cases, or are some tiers redundant?
  5. Do modern models reduce verifier-clean silent failures, especially evidence and root-cause failures?
  6. What does the cheapest/lowest-burden sufficient-model oracle look like with the new candidates?
  7. If specialization remains justified, which model is the best substrate after considering baseline quality, failure shape, training feasibility, and deployment simplicity?
Interpretation rule. A higher score is not enough. Explain which cases move, why they move, what failures remain, and what resource burden bought the improvement.

4. Scope and non-goals

In scope

  • cryptographic model/runtime provenance;
  • one modern small-Qwen arm;
  • TRAIN-only selection between the two Qwen3.8 quants;
  • Qwen3.8 DEV and conditional TEST;
  • Ternary Bonsai compatibility + DEV and conditional TEST;
  • offline R4, oracle, overlap, unique-rescue and dominance analysis;
  • runtime/footprint characterization.

Out of scope

  • QLoRA/SFT/RL/distillation or any weight changes;
  • new learned routers;
  • model-specific prompt tuning after DEV;
  • Suite v3/scorer/verifier/tool/evidence changes;
  • new frontier inference absent an integrity exception;
  • open-ended quant/model search;
  • H0-H3 harness work.

8. Split protocol

SplitAllowed use
TRAINCompatibility, cap/runtime calibration, Qwen3.8 quant selection, stability probes, gate design. No weight training.
DEVExactly one evaluation per frozen new execution system after the R6 contract commit. Used only to apply pre-registered TEST qualification.
TESTExactly once per DEV-qualified new candidate. No tuning or rerun afterward.

Generation budget

Use a deterministic TRAIN-only cap-calibration algorithm: start from the nearest existing practical tier budget, test only a small pre-declared cap set on a stratified TRAIN subset, and freeze the smallest cap meeting a pre-declared truncation tolerance. Exact pilot size/caps/tolerance must be committed before results are used.

11. Ternary Bonsai efficiency arm

Bonsai is a separate Qwen3.6-27B-derived compressed model requiring a compatible Prism runtime path. Before canonical trajectories, demonstrate exact artifact/runtime identity, FIS schema/tool compatibility, a successful TRAIN smoke set, and comparable resource capture.

Bound the integration. A thin runtime/provider adapter is allowed. Changing FIS task semantics, tools, evidence, scorer or verifier is not. If runtime integration is materially invasive, report BONSAI NOT RUN — RUNTIME INCOMPATIBLE FOR R6 rather than widening the milestone.

12. DEV qualification and TEST unlock

REGISTERED → TRAIN_COMPATIBLE → CONTRACT_FROZEN
→ DEV_EVALUATED → DEV_QUALIFIED | DEV_REJECTED
→ TEST_UNLOCKED → TEST_EVALUATED

Exact numeric gates must be committed before any new-candidate DEV inference. They may use historical Qwen/Nemotron/frontier DEV metrics and TRAIN-only candidate pilots, never new-candidate DEV.

  • Modern small: material improvement over Qwen3-8B without catastrophic reliability/resource regression.
  • Modern strong: competitive with/better than Nemotron, or within a pre-registered quality tolerance with a pre-registered operational advantage.
  • Bonsai: may use a lower strong-tier score only if it clears a pre-registered quality floor and demonstrates its intended material efficiency advantage.

TEST unlock binds artifact SHA, runtime digest, generation-config digest, DEV result digest and contract revision. No normal reset path. At most one Qwen3.8 quant reaches DEV/TEST.

14. R4 and oracle replay

For each new local model compute local-only quality, unchanged R4 cascade quality/utilization/FN/unnecessary escalation, post-answer ideal oracle, and oracle gap using frozen frontier trajectories.

Also compute descriptive tier orderings such as:

historical small → modern small → modern strong → frontier
modern small → modern strong → frontier
modern small → Bonsai → modern strong → frontier
modern small → Nemotron ↔ Qwen3.8 → frontier

Use actual latency/quality/pass-set evidence to determine where Nemotron belongs. Do not train or ship a new router in R6.

15. Integrity controls

  • Assert Suite v3/scorer/verifier digests at start and end.
  • Every new trajectory carries artifact SHA + runtime digest.
  • No new DEV before contract commit.
  • TEST state is fail-closed, monotonic and append-only.
  • No glob deletion/ad-hoc resets of canonical experiment state.
  • Adversarial reset/substitution tests use temporary registries.
  • Prefer clean-tree inference; otherwise explicitly hash only pre-permitted dirty paths.
  • Count every TRAIN/DEV/TEST/frontier call by artifact and wall time by phase.
  • Use replay for historical controls/frontier.
  • Run a small fixed TRAIN stability/reproducibility probe before DEV.

16. Multi-agent orchestration

Fable owns the scientific thread. Opus subagents do bounded work. Fable subagents are reserved for experiment-integrity review.

Main Fable owns

  • contract interpretation/amendments;
  • provenance acceptance;
  • quant/candidate eligibility;
  • DEV gates;
  • TEST unlock;
  • dominance/complementarity interpretation;
  • final next-step recommendation.

Default Opus work

  • inspection, registry implementation, runtime adapters, tests, provenance checks, metric recomputation, report consistency.

Fable independent reviews

  1. adversarial provenance + state-machine audit before DEV;
  2. pre-DEV contract/gate review;
  3. final challenge of dominance/substrate conclusions.

No agent teams by default. No parallel work across split boundaries. No subagent may decide to open TEST. Destructive adversarial tests must use temporary state.

19. Definition of done

  • Suite v3/R5 frozen scientific components unchanged.
  • Qwen3-8B exact official source/revision/SHA/size backfilled.
  • Both Qwen3.8 artifacts registered with exact Unsloth identities and distinguished from Bonsai.
  • Nemotron provenance complete enough to reproduce artifact/runtime.
  • Bonsai provenance/runtime requirement recorded.
  • Qwen3.5-9B acquired only from pinned source and digest verified before use.
  • Every new trajectory has model/runtime identity.
  • At most one Qwen3.8 quant reaches DEV.
  • Contract and numeric gates committed before new DEV.
  • Independent Fable pre-DEV audit passes.
  • Each eligible candidate gets one DEV; each qualified candidate gets at most one TEST.
  • No new frontier calls absent documented integrity exception.
  • R4/oracle/overlap/unique-rescue/dominance analyses complete.
  • Inference counts and wall time reported.
  • Full tests pass and tree is clean.
  • Final report recommends exactly one next milestone and does not start it.
